## 3. 优先修复项

### S1 · P2：搜索结果与回忆模式的目标页面冲突

**位置**：[wiki-slides.js](../../site/assets/wiki-slides.js)，基线第 841–845 行；同时参考 `initNote()`。

**触发步骤**：

1. 首页搜索 `Dataset-S2`。
2. 开启“先回忆”。
3. 点击 GenLIP 标题。

**已确认的逻辑结果**：标题链接为：

```text
notes/papers/2026-genlip.html?recall=1&from=q%3DDataset-S2#mechanism
```

首页仍用第一条搜索命中决定标题落点。该查询只命中完整笔记；完整笔记的 `initNote()` 不处理 `recall=1`，正文默认可见，因此不能兑现“先只看标题”的回忆流程。

**建议**：回忆模式下，论文标题统一进入该篇速览的回忆入口；普通搜索的片段链接继续负责定位实际正文。避免为修复这一条路径而给完整笔记复制整套回忆状态机。

**验收标准**：

- `Dataset-S2` 搜索后开启回忆，点击 GenLIP 只展示允许的标题与操作提示。
- 点击“显示检验问题”后才能看到具体问题，逐题展开答案。
- 退出回忆后恢复正常阅读。
- 普通搜索仍可直接进入完整笔记的命中位置，返回首页仍保留查询。

### S2 · P2：沿关联继续阅读会丢失来源筛选

**位置**：[wiki-slides.js](../../site/assets/wiki-slides.js)，基线第 355–380 行的 `buildContext()`，尤其第 370 行；手机重点关联链接也需一并检查。

**代码依据**：侧栏关联链接仅设置为 `target.href.split("/").pop()`，没有携带当前的 `from`。下一篇的顶部返回链接只能根据自己收到的 `from` 恢复首页条件。

**待浏览器复现路径**：首页按蒸馏专题和标签筛选 → 打开 U-OPSD → 通过侧栏关联打开 S²VOPD → 点击顶部“知识库”。预期回到原筛选，当前代码会回到无来源条件的首页。

**建议**：统一处理站内继续阅读链接的来源参数。覆盖侧栏、手机重点关联、文末关联、完整笔记出口和比较中的跨页依据；先确认各入口的产品含义，再复用现有参数处理函数。主动点击标签作为新的筛选操作，不必机械继承所有旧条件。

**验收标准**：

- 经一篇或两篇关联继续阅读后，顶部返回仍保留原有 `q/topic/tag/review`。
- 没有来源参数的直接访问保持正常。
- 参数不会重复嵌套或越传越长；浏览器后退仍正常。
- 原有速览与完整笔记往返路径不回归。

### S3 · P2：新增目录会触发旧搜索词的再次定位

**位置**：[wiki-slides.js](../../site/assets/wiki-slides.js)，基线第 1081–1125 行，尤其 `window.addEventListener("hashchange", locateHitText)`；新目录见 [完整笔记模板](../../site/_note-template.html)。

**代码依据**：`locateHitText()` 从 `from` 读取最初的搜索词，并在每次 hash 改变时，在目标章节内重新寻找该词并滚动。代码没有区分首次搜索进入与用户主动点击目录。

**待浏览器复现路径**：搜索 `Dataset-S2` → 进入 GenLIP 完整笔记 → 点击目录“我的复述” → 再点“关键机制”。只要目标章节包含原搜索词，目录点击就可能再次被定位到章节深处的命中文字，而不是章节开头。

**建议**：把“来源条件”和“本次定位意图”分开处理。首次搜索进入可执行精确定位；用户主动点击目录后遵循目录锚点。保留 `from` 用于返回，不要通过清空来源参数修复滚动问题。

**验收标准**：

- 首次从搜索进入仍直接看见命中文字。
- 后续点击目录到章节标题，不被原查询词再次拉走。
- “跳到正文”不被原查询词带到正文深处。
- 顶部返回保留来源；旧搜索定位样本和浏览器后退行为不回归。

### S4 · P2：索引生成器只重建部分字段，仍依赖旧投影

**位置**：[build-wiki-index.mjs](../../scripts/build-wiki-index.mjs)，基线第 14–20、120–127 行。

**已确认行为**：脚本先读取现有 `wiki-index.js` 中的专题、词表和页面清单，再更新页面标签及全文条目。专题归属、复测记录等仍沿用旧索引；新增页面也不会因出现在 Markdown 目录中而自动被发现。

**临时副本实验**：

| 项目 | 真源修改 | 重建结果 |
|---|---|---|
| U-OPSD 专题 | `topic: visual-encoders` | 仍为 `distillation` |
| U-OPSD 下次复测 | `review.md` 改为 `2099-01-01` | 仍为 `2026-10-07` |

实验未改动真实工作区；临时副本已清理。当前真实索引的复测数据是正确的，这项发现说明的是后续维护容易漏同步，并非声称目前日期已经错误。

**建议**：先让页面清单、front-matter 元数据、受控词表和结构化复测字段从各自真源生成，并对遗漏或不一致明确报错。速览提炼和关系说明包含编辑判断，应明确生成与校验边界，不要通过共享标签自动编造关系，也不要把未经核对的摘要当成新真源。

**验收标准**：

- 在临时副本修改专题、别名、标签和复测日期后，相关投影同步变化。
- 新增或删除页面后，生成器能够更新清单，或明确报告缺少对应派生文件；不能静默忽略。
- 连续运行两次结果一致；缺失真源、未知标签、无效落点能够被检查发现。
- 打开站点仍不需要运行构建命令或服务；保持静态与离线使用能力。

## 4. 后续优化项

### O1：让搜索优先找回具体困惑

当前 `matchingEntries(page, tokens).slice(0, 2)` 按原索引顺序选择首两条。搜索 `y+` 时，U-OPSD 展示“一页看懂”和“机制”，具体的 `qa-y-plus` 问答没有进入前两条。

建议增加轻量的条目排序，考虑问题标题、完整短语、具体问答和命中上下文；继续保留正文检索能力。标题入口与片段入口的职责也应清楚，尤其与 S1 一并处理。

验收例子：`y+` 能直接找到解释完整轨迹的问答；`流式 掩码` 能找到 VST 对应机制或卡壳问题；`Dataset-S2` 仍能找到完整笔记细节。不引入语义搜索服务即可完成这一轮优化。

### O2：手机首页把结果放在说明之前

[共享样式](../../site/assets/wiki-slides.css) 基线第 1796–1798 行对手机端 `.idx-side` 设置 `order: -1`，会把整个侧栏放到结果列表之前，包括“今天先做什么”和“阅读方式”。

建议在结果上方只保留紧凑的复测或回忆入口，把说明折叠或移到结果后。主阅读流程中的“Markdown 真源”“notes/”等维护术语可移入维护说明。完整笔记新目录也应检查手机占用，若明显挤压正文，可考虑默认折叠的原生 `details`。

本项是布局代码分析和设计建议，未实测首屏高度。请在 375×667 与 390×844 下比较修改前后首次结果的位置，并确认主要触控区域没有因压缩而变小。

### O3：把既有验收案例沉淀为可重复检查，再收拢样式

已有六轮报告包含有价值的失败样本。建议提取稳定的小型回归集，优先覆盖：

- 搜索 → 回忆；搜索 → 完整笔记 → 主动点击目录。
- 来源筛选 → 速览 → 关联 → 完整笔记 → 返回首页。
- 修改真源 → 重建索引 → 校验字段与锚点。
- 既有 `reward 信号`、`token 汇聚`、跨行内标签短语定位与高亮样本。

纯函数和静态一致性用本地脚本检查；滚动、焦点与遮挡用浏览器验证。没有实际运行的项目不能记为通过。

之后再合并 CSS 中迁移阶段留下的重复覆盖规则。当前共享 CSS 为 2106 行，交互 JS 为 1131 行；行数本身不是缺陷，目标是减少同一组件分散定义造成的修改遗漏。保留仍被页面使用的 class 和旧锚点兼容，不因重命名或抽象增加迁移范围。
